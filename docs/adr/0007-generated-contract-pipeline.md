# 7. One contract, generated outwards: Zod, then OpenAPI, then the typed client

- **Status:** Accepted.
- **Date:** 2026-11-23

## Context

The proposal chose REST with an OpenAPI document
([01 §5](../01-technology-stack.md#5-api-style--rest--openapi-generated-from-the-zod-contracts))
so that the API can be read without running it and a client can be typed against it.
Until the web client existed that was a sentence. The request schemas were Zod objects
in `packages/contracts`; responses were whatever a handler returned; no document
existed, and the first screen would have had to restate the API by hand.

There are three places an API's shape can be written down: the schemas the server
validates with, the document that describes it, and the types the client compiles
against. Written three times they drift, and the drift is found by a user.

## Decision

> **The Zod contracts and the route decorators are the only place the API's shape is
> written. The OpenAPI document is generated from them, the typed client is generated
> from the document, both outputs are committed, and CI fails when either is stale.**

```
packages/contracts (Zod)  +  @Validate / @Responds / @IfMatch / @Permission on routes
        -> apps/api/openapi.json           generated; a unit test fails when it is stale
        -> apps/web/src/lib/api/generated  generated by hey-api; CI fails when it is stale
```

- **Every route declares its response** (`@Responds(schema)`), as it already declared
  its input (`@Validate`). The response is *encoded through* the declaration: a field
  the schema does not name is never sent, and a result that does not fit is a 500
  `response_contract_violation`, not a leaked shape. A route with no declaration is
  refused before its handler runs. The document is therefore a description of what the
  server enforces, not of what someone remembered to write.
- **The document is produced by walking the real module graph**
  (`apps/api/src/openapi/`), the same walk that proves every route carries an
  authorization declaration. Requests render from the schema's input side, responses
  from its output side, `If-Match`/`ETag` appear where the decorators say, and every
  error status is the one shared body.
- **`apps/api/openapi.json` is committed** and `openapi.document.unit` fails when it is
  not byte-for-byte what the code generates. A change to the API's surface is always a
  reviewed diff in that file.
- **hey-api generates the client** (`@hey-api/openapi-ts`): TypeScript types, an SDK
  over a fetch client, and TanStack Query options and keys. It is committed, and CI
  regenerates it and fails on a difference. Screens never write a query key.
- **Forms import the Zod schemas from `@athlete/contracts` directly.** hey-api is not
  asked to generate a second copy of the schemas: the form validates the request it is
  about to send with the same object the API will validate it with.

## Options considered

- **`@nestjs/swagger` with DTO classes.** The framework's default. It needs every
  request and response restated as a decorated class, beside the Zod schema that
  actually validates; the two agree only by discipline
  ([01 §10](../01-technology-stack.md#10-tooling-defaults-named)).
- **Write `openapi.json` by hand.** Readable, and wrong the first time a route changes
  without it.
- **tRPC, or importing the API's types into the client.** No generation step at all.
  Gives up the language-agnostic contract that was the reason for REST, and ties the
  client to the server's module graph.
- **Generate at build time and commit nothing.** Fewer generated lines in review. A
  change to the contract would then be invisible in a pull request, and the client
  could not be type-checked without first building the API.
- **Let hey-api generate Zod schemas too.** One import for forms. Two copies of each
  schema, one of them derived through JSON Schema and so subtly different (defaults,
  coercion, refinements do not survive the round trip).

## Consequences

- **Good:** renaming a field in a contract breaks the client's type-check in the same
  pull request. The route manifest, the document and the client cannot disagree with
  the code, because each is a test failure when it does.
- **Good:** a response cannot leak a column. A handler that returns a whole row sends
  only what its schema names (`response.http` asserts it).
- **Cost: two regeneration commands** after a contract or route change
  (`UPDATE_OPENAPI=1 pnpm --filter @athlete/api run test`, then
  `pnpm --filter @athlete/web run generate`), and generated files in every such diff.
- **Cost: the generator is ours.** About the size of the route walk it shares; it knows
  only the decorators this API uses, and a new kind of declaration has to be taught to
  it.
- **Limit: error `meta` is an open record in the document.** Its shape depends on
  `code`, so the client's error mapper types the one case it reads (the invalid
  `fields` of a validation failure) by hand against `packages/contracts`.
- **Limit: better-auth's routes are not in the document.** `/api/auth/*` is the
  library's API ([ADR 0006](./0006-cookie-sessions-and-the-auth-role.md)); the SPA
  calls it through the library's own client.
- **Not a mechanism the API has:** an `Idempotency-Key` header. Earlier drafts of the
  proposal named it as a REST mechanic. What makes a retried attendance submission
  safe is in the body, where the contract can type it: a client-generated
  `clientRecordId` on each entry, unique per academy.
